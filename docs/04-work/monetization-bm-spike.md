# 비광고 BM 검토: 광고 제거 IAP / 보상 패스 (스파이크)

happy-farm은 현재 **광고 only** 수익화다(보상형 5지면 + 전면 2지면, `packages/farm-core/src/ads.ts`).
광고 거부 성향 유저(시청률이 낮은 세그먼트)는 사실상 수익에 기여하지 못한다. 이 문서는
이 세그먼트를 흡수할 **비광고 옵션**의 타당성을 LTV 영향·캐니벌라이제이션·구현 비용
관점에서 비교하고 권고안과 후속 구현 범위를 정의한다. (관련 이슈: [M8])

> 스파이크 문서이므로 수치는 도입 전 검증이 필요한 **가설**이다. 실제 의사결정은 GA4
> 코호트(광고 시청 분포)와 스토어 매출 리포트로 검증 후 진행한다.

## 1. 현황 요약 (코드 기준)
- **광고 지면**: `REWARDED_AD_PLACEMENTS`(shop_gold_reward, shop_plot_discount, growth_ad_sheet,
  harvest_bonus_sheet, return_offline_bonus) + 전면(milestone, return_welcome_back).
- **전역 토글**: 광고 on/off는 Remote Config `mobile_ads_global_enabled`로 이미 제어된다
  (mobile: `apps/mobile/src/ads/policy.ts`, AIT: `apps/ait/src/firebaseWeb/remoteConfig.ts`).
  → **광고 제거 entitlement가 생기면 이 토글 경로를 그대로 재사용**해 유저 단위로 광고를 끌 수 있다.
- **빈도/cap**: `ad_limits_overrides`(farm-core `adLimits.ts`)로 원격 조정 가능.
- **IAP 인프라**: **없음**. `react-native-iap`/Play Billing/StoreKit/영수증 검증/구매 복원/
  entitlement 영속화 모두 미구현. 분석에도 구매 이벤트(`purchase`/`iap_*`) 없음.
- **세이브/복원**: 로컬 세이브 + (mobile) `cloudBackupCore` 존재 → entitlement 영속화의 토대로 활용 가능.

## 2. 옵션 정의
- **A. 광고 제거 IAP** — 1회성 비소모성(non-consumable) 상품. 구매 시 광고 전역 비활성.
  (선택지: 영구 1회성 vs 월 구독. 본 스파이크는 **영구 1회성**을 기본안으로 본다 — 단순·신뢰·환불 적음.)
- **B. 보상 패스(시즌/배틀 패스)** — 기간제 트랙. 무료/유료 2열, 진행도(수확·졸업 등)로 티어 보상 해금.
  광고는 유지하면서 **추가 가치**를 판매(광고를 끄지 않음).
- **C. 혼합** — A를 먼저 출시해 ad-rejector를 흡수하고, IAP 인프라가 안정된 뒤 B를 시즌 콘텐츠로 추가.

## 3. 평가
### 3.1 LTV 영향 (가설)
- **A**: ad-rejector(광고 ARPDAU ≈ 0)에게서 **증분 매출**. 광고 ARPDAU가 낮을수록 광고 제거 가격이
  쉽게 LTV를 상회한다. 결제 의향이 있는 소수 고관여 유저의 LTV를 끌어올린다.
- **B**: 고관여·리텐션 좋은 유저의 LTV 상단을 키운다(반복 결제 가능). 단, 무료 트랙이 리텐션을
  끌어올려 **광고 임프레션도 함께 증가**할 수 있어 광고 매출과 시너지.
- **A+B 공존**: A 구매자는 광고가 꺼지므로 B의 무료 트랙 광고 시너지에서 빠진다(부분 상충).

### 3.2 캐니벌라이제이션
- **A**: 광고를 "끄는" 상품이므로 구매자의 잔여 광고 매출을 잠식. 단 **타깃이 ad-rejector**라
  원래 광고 매출이 작아 **순잠식은 낮음**. 핵심은 가격을 *기대 잔여 광고 LTV 이상*으로 책정하는 것.
  고시청 유저가 싸게 광고를 끄면 잠식이 커지므로 **가격·세그먼트 모니터링 필수**.
- **B**: 광고를 끄지 않으므로 광고 매출 잠식 거의 없음(**additive**). 다만 유료 패스가 기존 보상형
  광고 보상(골드/부스트)과 겹치면 보상형 광고 수요를 일부 잠식할 수 있어 보상 설계 분리 필요.

### 3.3 구현 비용
| 항목 | A 광고 제거 | B 보상 패스 |
|---|---|---|
| 스토어 상품 등록(Play/App Store) | 1개 비소모성 | 패스 상품(기간/시즌) + 갱신 운영 |
| 결제/영수증/복원 | 필요(공통 토대) | 필요(공통 토대) |
| Entitlement 영속화 | 단순(boolean, 세이브/클라우드) | 복잡(시즌·티어·클레임·만료 상태머신) |
| 게임 로직 변경 | 최소(광고 토글 재사용) | 큼(진행도→티어 매핑, 보상 지급, UI) |
| 라이브옵스 | 없음 | 큼(시즌 콘텐츠 주기적 공급) |
| AIT(Toss) 결제 | **미확인**(아래 4절) | **미확인** |
| 상대 규모 | **S–M** | **L** |

### 3.4 플랫폼 제약
- **Google Play / App Store**: 표준 IAP(`react-native-iap` 등)로 A·B 모두 가능. `apps/mobile`.
- **AppsInToss(Granite)**: Toss 슈퍼앱 내 실행. 표준 스토어 빌링이 적용되지 않아 **Toss 결제 API
  지원 여부 선행 조사 필요**(이슈 #74의 푸시 가용성 조사와 동일한 성격의 미확인 항목). 미지원이면
  AIT는 광고 only를 유지하고 A/B는 **mobile 우선** 출시로 분리한다.

## 4. 권고안
1. **A(광고 제거, 영구 1회성)를 1차로 추진한다.** 가장 낮은 구현 비용/낮은 순잠식으로
   ad-rejector를 흡수하고, 이후 모든 IAP의 **공통 결제 토대**(빌링·영수증·복원·entitlement)를 먼저 검증한다.
   광고 비활성은 기존 Remote Config 토글 경로를 재사용하므로 게임 로직 변경이 최소다.
2. **B(보상 패스)는 2차로 보류한다.** LTV 상단 확장 잠재력은 크지만 상태머신·UI·라이브옵스 비용이
   L급이고, 무료 트랙 광고 시너지와 A의 광고 제거가 부분 상충한다. A의 결제 토대가 안정된 뒤 재평가한다.
3. **AIT 결제는 별도 조사 이슈로 분리**(Toss 결제 API 가용성). 미지원 확정 시 AIT는 광고 only 유지.
4. **가격은 잔여 광고 LTV 기반으로 책정**하고, 출시 후 세그먼트별 잠식을 모니터링(아래 측정 계약).

## 5. 후속 구현 범위 (Phase 정의)
도입 결정 시 아래 단위로 이슈를 분할한다(본 스파이크의 산출물).
- **P0 공통 결제 토대**: `react-native-iap` 통합, 상품 조회, 구매/복원, 영수증 검증(서버 또는 스토어
  단), `entitlements`(예: `adsRemoved: boolean`) 게임 상태/세이브·클라우드 동기화, Remote Config로
  IAP 노출 토글. (`apps/mobile`, `packages/farm-core/src/types.ts` 정규화, 클라우드 백업)
- **P1 광고 제거 상품(A)**: 스토어 상품 1개, 구매 플로우 UI(상점/설정), 구매 시 광고 전역 off
  (`mobile_ads_global_enabled` 경로 재사용한 per-user entitlement), 복원 진입점.
- **P2 분석**: `iap_impression`/`purchase`/`purchase_restored`/`purchase_failed`(상품ID·가격·placement),
  세그먼트별 광고 잠식 리포트 기준.
- **P3 AIT 결제 조사**: Toss 결제 API 가용성 스파이크 → 가능 시 A 이식, 불가 시 광고 only 유지 명시.
- **P4 보상 패스(B)**: 별도 대형 트랙(시즌 정의·진행도 매핑·티어 보상·클레임/만료 UI·라이브옵스).
  P0~P2 안정화 후 재평가.

## 6. 리스크
- **가격 미스 → 과잠식**: 고시청 유저가 싸게 광고를 끄면 광고 매출 잠식이 증분 매출을 상회. 가격
  실험 + 세그먼트 모니터링으로 관리.
- **AIT 결제 미지원**: 플랫폼 간 BM 비대칭 발생. 조사로 조기 확정.
- **영수증/복원 미흡 → CS·환불**: 공통 토대에서 복원·검증을 우선 견고화.
- **B의 라이브옵스 부담**: 시즌 콘텐츠 공급이 끊기면 가치 하락. A 안정화 전 도입 금지.
