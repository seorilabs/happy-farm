## 목적과 근거

광고 SDK가 보상 획득을 알린 뒤 표시 오류가 와도 획득 상태를 보존하고, 서버가 검증한 보상을 한 번 지급한다. 앱인토스 수정과 모바일 수정을 새 후보에 함께 담아 운영에 반영한다.

2026-11-05 10:37 KST 앱인토스 문의는 번들 `20261024-55`, 토스 `5.283.0`, iPhone 13 Pro Max에서 광고 표시 오류가 반복되고 보상을 받지 못한다는 내용이었다. 원 문의의 실제 이벤트 순서는 로그 조회 403으로 아직 확인하지 못했다. 식별 키와 디바이스 ID는 설계·코드·PR에 옮기지 않는다.

앱인토스는 PR #598로 수정·병합됐지만 운영 배포는 별도 상태다. 이후 실제 모바일 출시용 `createPlatformAdMobAdapter`에 Android·iOS를 각각 지정하고 보상 획득 뒤 오류를 주입했으며, 두 테스트 모두 기대 `earned` 대신 `failed`를 반환해 실패했다. 이는 개발 환경 재현이며 실제 기기·광고 공급 또는 원 문의의 원인 확정 증거가 아니다.

원본은 `/Volumes/Data/Backup/agent-artifacts/happy-farm/2026-11-06/8633a02bb7c001501aa5c9a558802ef99c5b36b6/platform-scope-065243Z-026273a1`의 테스트·로그·검증 manifest에 보존했다. 해당 모바일 어댑터와 서버 검증 wrapper는 `v1.13.0` 이후 바뀌지 않았다.

## 전후 흐름과 책임

| SDK 및 서버 상태 | 현재 모바일 결과 | 수정 후 결과 |
|---|---|---|
| 보상 획득 뒤 `ERROR` 또는 show Promise 실패 | SDK 결과가 failed여서 서버 보상 확인에 진입하지 못함 | 획득 상태를 보존하고 원래 claim의 서버 검증 진행 |

| 서버 pending·expired·client_confirmed 또는 조회 오류 | 지급 안 함 | 지급 안 함, 기존 실패 계약 유지 |

| 요청 폐기·unmount·다음 세대로 전환 | 취소·현재 세대 가드 적용 | 기존 계약 유지, 폐기를 지급 성공으로 바꾸지 않음 |

`apps/mobile/src/ads/adMobRewardedAd.ts`의 출시용 어댑터와 개발용 훅에서 **실패 결과를 확정할 때** 이미 받은 유효한 보상 획득 상태를 우선한다. 보상 객체와 Android의 닫힘 경과시간 진단을 보존한다. 정상 종료 전 지급을 앞당기지 않으며, 기존 `OPENED` 이후 시간 제한 해제와 Android의 닫힘 후 500ms 유예도 유지한다. 명시적인 요청 폐기와 오래된 콜백을 새 요청의 성공으로 바꾸지 않는다.

`apps/mobile/src/ads/platformRewardedAd.ts`는 SDK 결과와 서버 지급 허가의 경계다. SDK 결과 보존 뒤에도 기존 `confirmed|delivered` 및 `server_verified` 조건을 반드시 통과해야 최종 `earned`와 claim ID를 UI에 반환한다. pending·만료·미검증·조회 실패를 성공으로 바꾸거나 직접 보상을 지급하지 않는다. wrapper의 제품 동작 변경은 계획하지 않으며 실제 어댑터와 연결한 회귀 테스트로 이 계약을 고정한다.

공통 `FarmGame`의 claim ID 중복 방지, 보상·사용 횟수의 원자적 상태 반영, 로컬 저장 후 ack 흐름은 재사용한다. 공통 UI에는 새 지급 경로를 만들지 않는다. 동일 저장 상태의 자동 저장과 명시적 저장은 기존 동작이며, 저장 API 호출 횟수 대신 보상과 사용량이 1회만 증가하는지 확인한다.

## 범위와 대안

제품 변경은 모바일 광고 결과 보존과 관련 테스트에 한정한다. 앱인토스 수정은 새 후보에서 다시 검증한다. UI·문구·보상 수치·저장 형식·SDK·광고 단위·SSV 설정·권한·개인정보 정책을 변경하지 않는다. 별도 리팩토링이나 임시 호환 계층은 필요 없다.

SDK 보상 신호만으로 공통 UI에 즉시 지급하는 방법은 서버 검증 계약을 깨므로 채택하지 않는다. 앱인토스만 먼저 배포하는 방법은 두 모바일 앱에 재현된 결함을 남기므로 이번 후보는 세 마켓을 함께 준비하되, 외부 심사와 공개 상태는 마켓별로 독립적으로 진행한다.

현재 게임에는 8개 UI 로케일이 있다. 사용자 문구의 변경은 없으며 마켓 출시노트만 검증된 수정 내용으로 각 활성 언어에 맞춰 갱신한다. 제목·설명·이미지·개인정보 등 기존 등록값도 제출 전 해당 마켓의 모든 활성 언어를 검수하고 실제 저장값을 다시 읽는다. App Store 문구에는 다른 마켓 이름을 넣지 않는다.

## 운영 확인, 복구와 승인 경계

기존 활성 자격증명만 재사용한다. 새 키·계정·권한·프로덕션 리소스를 만들거나 가격·국가·결제 상품·정산을 바꾸지 않는다. 파이프라인 수정, 새로운 제품·정책 판단, 수동 보상·데이터 복구, 지원팀 연락은 별도 범위다. 실패 후보 태그를 이동하지 않으며 범위 안 제품 결함은 PR과 새 후보로 수정한다. 공개 후 회귀는 배포 원본·버전·이벤트를 보존하고 수정 후보로 대응한다.

원 문의의 로그 조회 403은 기존 읽기 경로에서 원인을 조사하되 권한을 임의 확대하지 않는다. 복구되면 문의 시점의 로드·표시·획득·서버 검증·지급 기록을 대조하고, 출시 후 관측 가능한 시도·완료·실패 지표를 마켓별로 확인한다. GA4 AIT 누락을 0건으로 해석하지 않고 측정 불가·지연·실패를 구분한다. 운영 지표를 관측하지 못하면 코드 공개와 효과 미확인을 별도 상태로 보고한다.

모든 원시 로그·provider 응답·서명 산출물·검수 자료는 NAS1dual에 스트림 복사해 크기·SHA-256을 직접 대조한 뒤 작업 전용 로컬 사본을 정리한다. Git에는 코드·필요한 텍스트 요약과 NAS 위치만 남긴다.
